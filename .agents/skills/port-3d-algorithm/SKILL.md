# port-3d-algorithm 技能说明

## 适用场景

把一段复杂的 3D 算法（例如 Blender 的 iksolver、某个 DCC 的蒙皮/约束算法）复刻到目标引擎（UE Control Rig、自研引擎等）。这类移植最容易翻车的不是算法本身，而是**参数语义**和**坐标系约定**在源实现与目标环境之间悄悄发生了变化。

## 核心工作流程（严格按顺序，不可跳过）

```
阶段1: 阅读理解原代码（含参数/坐标系盘点）
   ↓
阶段2: 写 Python 模拟验证移植后的算法（用真实数据，务必可运行）
   ↓
阶段3: 写移植后的实现代码（逐项映射，带坐标系检查）
```

## 阶段 1：阅读理解原代码

### 1a. 通读算法核心，画出数据流

不要急着写代码。先回答三个问题：

- 这个算法在**迭代/循环**里每次在做什么？（例如：重建雅可比 -> 求伪逆 -> 应用角度 -> 位置级联）
- 输入是什么、输出是什么、中间状态是什么？
- 每一步用到哪些参数？

把算法的数据流画出来（例如用 mermaid 或文字），确保理解整体，而不是只盯局部。

### 1b. 参数盘点表（本技能最重要的步骤）

**原代码里出现的每一个参数/变量，都要记录到一张表里**，至少包含四列：

| 参数 | 含义 | 单位 | 坐标系/空间 |
|------|------|------|-------------|
| `goal` | 末端目标点 | 长度单位（厘米/UE单位） | 全局/世界空间 |
| `clamp_length` | 位置残差钳制上限 | 长度单位 | 全局空间 |
| `axis` | 骨骼旋转轴 | 无（单位向量） | 骨骼的**全局**旋转坐标系 |
| `m_basis` | 骨骼局部旋转 | 弧度（旋转矩阵） | 相对父骨骼（局部空间） |
| `dtheta` | 角度增量 | 弧度 | 全局轴系（与 axis 一致） |
| ... | ... | ... | ... |

**规则：**
- 每一个读入的、算出的、传参的量都要进表。漏掉一个，可能就是后面 bug 的来源。
- 标注**空间**：局部（相对父）/ 全局（相对世界或根）/ 某个特定基准。
- 标注**旋转约定**：行向量还是列向量、左乘还是右乘、右手还是左手坐标系。
- 标注**单位**：弧度还是角度、毫米还是厘米、是否带缩放。

### 1c. 坐标系/约定检查清单（逐项打钩）

对原代码里的每个几何量，逐项确认：

- [ ] 位置：局部 / 全局 / 世界？基准点是谁？
- [ ] 旋转：存的是四元数、欧拉角还是矩阵？旋转顺序？
- [ ] 旋转应用方向：`R_new = M * R_old`（左乘/预乘，绕**全局固定轴**）还是 `R_new = R_old * M`（右乘/后乘，绕**局部轴**）？**这两者数学上不等价，且迭代稳定性可能完全不同**——这是最容易翻车的地方。
- [ ] 矩阵/四元数乘法顺序：列向量 `v' = R * v` 还是行向量 `v' = v * R`？
- [ ] 轴的定义：雅可比/约束里的 axis 是全局轴还是局部轴？
- [ ] 符号：`p × axis` 还是 `axis × p`？残差是 `goal - pos` 还是 `pos - goal`？符号反了第一步就会错。
- [ ] 弧度 vs 角度：所有三角函数、角度增量是否统一？
- [ ] 左手 vs 右手：`CrossProduct` 的方向、`Atan2` 的叉积分量顺序是否符合目标环境的坐标系。

## 阶段 2：写 Python 模拟验证（移植的"安全网"）

**在写任何目标语言实现之前，先用 Python/numpy 严格复刻算法并跑通。** 这是验证"我理解的算法对不对"最廉价的方式。

### 2a. 用真实数据，不用玩具数据

- 从运行日志、断点、或源引擎里抓**真实的输入数据**（真实的骨骼位置、目标点、参数值）喂给 Python。
- 如果可能，也抓取源实现的**中间输出**（例如每一步的距离/角度），用于对比。

### 2b. 严格逐行复刻，不"优化"

- Python 代码要逐行对应原算法的每一步，连阻尼系数、钳制、收敛阈值都要一致。
- 数学库用 numpy（SVD、矩阵、四元数）即可，但**逻辑分支、系数、clamp 必须照抄**。

### 2c. 用"复现现象"来定位根因

- 如果移植后目标实现表现异常（不收敛、发散、位置错误），**先在 Python 里复现这个现象**。
- 例如：真实数据显示"先收敛到 0.3 再发散到 8"，就在 Python 里跑同一份数据，看是否复现。能复现 -> 在 Python 里改、验证、找到根因 -> 再改目标代码。**不要直接在目标代码里瞎试参数。**
- 常见做法：写一个对比脚本，把"当前实现"和"几种候选修复"（不同系数、不同旋转方向）并排跑，用表格对比谁收敛、谁发散、收敛精度多少。这一招能瞬间暴露真正的根因。

### 2d. 验证维度

- **收敛性**：迭代多少次收敛？是否单调平滑（还是先降后升的振荡）？
- **精度**：最终残差多少？是否达到要求的精度？
- **稳定性**：不同参数（如最大步长、阻尼系数）下是否稳健？可达 vs 不可达场景分别验证。
- **几何性质**：移植后算法的关键性质（如"pole 不改变末端位置""末端保持在目标上"）用数值验证（残差应 ~0，位置变化应 ~0）。

## 阶段 3：写移植后的实现代码

### 3a. 逐项映射，带坐标系检查

把阶段 1 的参数盘点表逐行翻译到目标语言/引擎：

- 每个参数在目标环境里对应的 API/字段是什么？
- 目标环境是否改变了坐标系/约定？（例如：UE 是左手、Z 向上、厘米；Blender 是右手、Z 向上、米。旋转矩阵/四元数的约定也要确认。）
- 目标环境的数学库差异：例如 UE 5.7 LWC 里 `FVector = TVector<double>`、`FQuat` 没有 `ToMatrixNoScale()`、`ToAxisAndAngle` 返回的角度类型等——**这些 API 差异会在移植时悄悄引入坐标系/精度 bug**。

### 3b. 保留可诊断性

- 移植后保留调试日志（关键中间量：初始状态、每步残差/角度、奇异值、收敛判断），方便对照 Python 模拟的输出验证移植是否正确。
- 日志格式要和 Python 模拟的打印对齐，方便 diff。

### 3c. 实现与模拟对照验收

- 用同一份真实数据，让目标实现和 Python 模拟各跑一遍。
- 对比：初始残差、每步残差、最终残差、迭代次数、关键中间量。应一致（允许浮点级误差）。

## 本技能的真实案例（供参考）

以下来自一次 Blender iksolver -> UE Control Rig 的移植，展示了每个陷阱的典型症状：

| 陷阱 | 症状 | 根因 | 教训 |
|------|------|------|------|
| 旋转应用方向写反（左乘 vs 右乘） | 先收敛到 ~0.3 再振荡发散到 8+，不收敛 | Blender 是 `m_new_basis = m_basis * M`（右乘局部），被写成"全局左乘+手动传播下游" | 迭代稳定性高度依赖旋转应用方向；用 Python 并排跑"左乘 vs 右乘"秒定位 |
| 局部偏移在 Pos 未赋值时计算 | 链长虚高到 322，一步甩飞 | 计算 `LocalOffset[i]` 时 `Pos[i+1]` 还是 (0,0,0) | 有依赖关系的量必须拆独立循环、按序赋值 |
| 末端骨骼长度被丢弃 | 末端骨骼雅可比列为 0，位置算不准 | 链末端错误地用了"最后一根骨骼的根点"而非其 tail | 明确"链末端"在源实现里到底指哪个点 |
| 用"修正算法"掩盖不收敛 | 位置看起来对，但算法本身从未收敛 | 加了 FABRIK 收尾强行把残差压到 0，掩盖了雅可比发散 | 先让核心算法真正收敛，再谈修正/兜底；不要用兜底掩盖真 bug |
| 参数语义理解错 | 用户设的精度不生效 | 收敛阈值被 `min(Precision, 1e-3)` 覆盖 | 参数就是参数，直接使用用户设定，不做隐式裁剪 |
| 阻尼系数随意改 | 误以为系数是发散根因 | 真实根因是旋转方向，系数只是背锅 | 用 Python 对比脚本区分"真因"与"背锅参数" |

## 验收清单（写完后逐项打钩）

- [ ] 原代码的每一个参数都进了盘点表，且标注了含义/单位/坐标系
- [ ] Python 模拟用真实数据跑通，且能复现（或解释）目标实现的任何异常
- [ ] 目标实现与 Python 模拟用同一数据对照，残差/迭代次数一致
- [ ] 坐标系逐项检查完成（左右手、行/列向量、左/右乘、全局/局部、弧度/角度）
- [ ] 关键几何性质用数值验证（如"某约束不改变某位置"）
- [ ] 调试日志保留且与模拟对齐
